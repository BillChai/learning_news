1. **[工程知識/DB] PostgreSQL：如何對「非分區鍵」欄位也做到 partition pruning**
   Haki Benita 示範一個進階技巧：即使查詢條件不是分區鍵，也能靠在分區表上加「精心設計的 CHECK constraint（定義多段 range，靈感來自 multi-minmax BRIN operator）」讓 planner 剪掉不相關分區——解決「分區鍵與實際查詢欄位相關但不同」的常見痛點。實務性很高的 DB 調校文。

2. **[工程知識/架構] 積壓的數學：佇列恢復的容量規劃**
   把「backlog 到底多久能消化」化成可算的公式：drain time 取決於「總處理率 − 到達率」的剩餘容量，並給出 headroom 公式（所需 consumer 數 = 穩態 consumer + 積壓 ÷（處理率 × RTO））；還點破 retry amplification 會把系統推入 metastable 故障——即使根因已修，積壓仍自我維持。做佇列/自動擴縮容量規劃的必讀。
   來源：InfoQ（The Mathematics of Backlogs）— <https://www.infoq.com/articles/capacity-planning-queue-recovery/>｜發布：2026-05（較早）｜配額類別：工程知識/教學｜來源類型：優先來源清單（InfoQ）

4. **[工程知識/後端] Rate Limiting 演算法：Token Bucket vs Sliding Window vs Fixed Window**
   把四種主流限流演算法（fixed window、sliding window、token bucket、leaky bucket）的機制、記憶體成本與突發流量容忍度拆開比較，並給出選型準則：多數 API 用 sliding window counter 在精度/簡單/低記憶體間最平衡；需要可控突發用 token bucket，要嚴格平滑用 leaky bucket。做 API gateway/限流的實用指南。

13. **[Kotlin] Ktor 3 的 Structured Concurrency：請求管線的失敗隔離**
    聚焦一個實戰陷阱：在 Ktor route handler 裡用預設 `coroutineScope` 平行打多個上游時，只要一個外部呼叫逾時，兄弟 coroutine（連 DB、cache 這些已拿到可用資料的）也會被一起取消；解法是改用 `supervisorScope` + `CoroutineExceptionHandler` 做失敗隔離，避免單一慢上游拖垮整個服務。與 07-23 的「structured concurrency 概念詳解」是不同層次的實作落地。
    來源：MVP Factory Blog — <https://mvpfactory.io/blog/structured-concurrency-in-ktor-3-with-kotlin-coroutines-supervising-request/>｜發布：2026-06-05（較早）｜配額類別：工作技術棧（Kotlin）｜來源類型：開放搜尋補充
